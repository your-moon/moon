## What changed

- **#25 reads overlay queued writes.** `readIndex` (the one path ls, show, frontier, claims, milestones, status and the TUI share) now applies the queued `close`, `reopen`, `label`, `milestone` and `edit` ops of each issue over its mirror row, in queue order. Derived status follows because it is computed from the overlaid row (and `isOpen` for dependencies). A queued `new` was already listed as `(pending sync)`. Ops whose last send failed (`last_error` set) stop overlaying; dropping an op removes its file, so it stops too. Pull's `rebuildIndex` reads `readIndexRaw`, so the overlay never leaks into the mirror. See `internal/issues/overlay.go`.
- **#17 parallel sync.** `push` runs a pool of `pushWorkerLimit = 4` writes at once, started as slots free up. Order is kept per issue (the writes of one ref, which includes a `new` before the edits on its local ref, until the create lands and refs are rewritten), per repo for milestone writes, and `msWaiting` still holds issue writes behind a queued milestone. The longest chains start first. Results (outbox removal, localmap, ref rewrite, failure bookkeeping) are applied by one goroutine. Failures stay per op: the failed op records `last_error`, its issue's later writes wait, others go on.

## Why

Reads were stale until a GitHub round trip; sync took ~3-4 s per queued write, one at a time.

## Verification

`go vet ./...`, `go test -race -count=1 ./...` green.

Pool size, fake gh with 100 ms per call, 17 writes (12 closes on separate issues, a new + comment + label + close chain, a label behind a close), `MOON_POOL_BENCH=1 go test ./internal/issues -run PoolSizes -v`:

| workers | time |
| --- | --- |
| 1 | 1.76 s |
| 2 | 0.95 s |
| 4 | 0.51 s |
| 8 | 0.44 s |
| 16 | 0.44 s |

Kept 4: 3.4x faster than serial and within 15% of the floor (the 4-call chain). More workers add little and raise the risk of GitHub's secondary rate limit on concurrent writes.

Mutations that turn tests red: skipping the overlay; not skipping failed ops; dropping the per-issue order; dropping the in-flight key; ignoring the pool limit; ignoring `msWaiting`.

Tests that assert a global gh call order set `serialPush`. Test handlers are serialised by default (`fakeGH.parallel`).

## Left from #18, and why

Not done: async background push after every write, GraphQL batching of writes, and since-based pull deltas. Each is its own design (lock and debounce for the detached run, a GraphQL mutation builder with local-ref resolution between requests, a new pull query) and cannot be verified without the network. #17 cuts the wait to about the longest chain; writes already return as soon as they are queued. #18 stays open for those three.

Also not changed: `show` still lists failed ops in its "effective state" line (it prints their last error).
